## HeartFlow 恋爱模拟器 — 产品说明

HeartFlow 是一款本地运行的恋爱对话训练工具。它不是教你"话术套路"的 PUA 脚本，而是一个让你练习真实、有分寸、有边界感的亲密关系沟通能力的模拟器。

核心理念来自《一门给年轻人的恋爱成长课》：恋爱不只靠感觉，感觉提供动力，理性负责方向、边界和长期经营。HeartFlow 把这个理念做成了一个可以反复练习的互动界面。

---

### 它能做什么

**对话模拟。** 你在一个仿微信聊天界面里和 AI 扮演的女性角色对话。每次发送消息前，系统会分析你的回复，给出隐藏意图解读、A/B/C 三种风格的回复建议，以及教练评分。

**三个内置角色，风格各异：**

- 林知夏 — 23 岁，研一，慢热知性型。边界感强，讨厌油腻和过早暧昧。
- 许砚秋 — 24 岁，互联网产品经理，理性直球型。看重清晰真诚的沟通，不吃套路。
- 唐一禾 — 22 岁，艺术社团，活泼感受型。喜欢轻松有画面感的互动，讨厌冷场和说教。

你也可以自定义角色 — 设定姓名、性格标签、角色逻辑、开场白，保存后直接切换。

**教练层（Coach Layer）。** 右侧面板实时显示：

- 隐藏意图分析 — 她这句话背后可能在观察什么
- A/B/C 三种回复 — 温柔高情商 / 幽默风趣 / 拉扯试探，根据当前阶段和你的风格偏好排序
- 长期对话路线 — 生成未来几轮的推进计划
- 教练评分 — 从自然度、共情、边界感、推进力四个维度打分，指出亮点、短板和下一步练习方向

**发送前测验（Preflight）。** 点"发送前测验"，系统会检测越界词、施压词、问题过多、句子过长等风险，在发送前就给你修正建议。

**训练阶段选择。** 支持 7 个阶段：刚加微信后的第一晚、隔天轻联系、第一次邀约、第一次约会后、暧昧推进、表达好感、确定关系。每个阶段影响 AI 的角色行为和建议尺度。

**场景记忆。** 可以设定关系背景、她的兴趣爱好、雷区和禁忌，让模拟更贴近你的真实场景。

**头像自定义。** 上传角色头像图片，支持拖动和滑杆微调取景位置。

**长篇恋爱模拟文本。** 项目附带一部 17.4 万字的 10 章长篇对话小说（夏紫桐系列），记录了两位同龄人从重新联系到长期经营的完整过程。每章穿插恋爱大师复盘，指出每句话的好处、风险和更好的表达方式。这不是爽文，而是写实的练习教材。

### 技术架构

```
relationship-simulator/
├── heartflow-c/               # C 版运行时（重构目标）
│   ├── src/main.c             # 命令分发：CLI + serve
│   ├── src/server/            # HTTP 服务、7 个 API、关系智能运行时
│   ├── src/voice/             # TTS 文本清洗 / 分句 / RMS / WAV 封装
│   ├── src/tools/             # hf check circular（替代 JS 门禁脚本）
│   ├── src/json.c             # 自写 JSON，无外部依赖
│   └── hf.exe                 # 单文件可执行（约 445 KB）
├── voice/                     # 语音模型推理（PyTorch / onnxruntime，仅保留 load+infer）
├── server/                    # Node 参照实现（14 个 JS 文件，保留对照）
├── public/                    # 前端静态资源（HTML / CSS / 模块化 JS）
│   ├── index.html             # 三栏布局主界面（角色面板 / 聊天 / 教练层）
│   ├── app.js                 # 前端主逻辑（状态管理、UI 交互、LLM 调用）
│   ├── styles.css             # 界面样式
│   └── modules/               # 教练、回复、隐私、记忆等前端模块
├── long-simulation/           # 17.4 万字长篇模拟（10 章）
├── .agents/skills/relationship-coach-cn/
│   └── runtime/               # 关系智能 JS 原始实现（已移植到 C）
├── generate-long-simulation.mjs  # 长篇模拟生成脚本
├── validate-long-simulation.mjs  # 长篇模拟校验脚本
├── .env.example               # 环境变量模板
└── test/                      # Node 单元测试（参照实现）
```

**默认运行时是 C 版**：`heartflow-c/hf.exe serve` 提供静态站与 7 个 API，零外部依赖、单文件、
出站 HTTPS 走 Windows 自带的 WinHTTP。Node 版（`server/`）保留为对照实现：两者的
`/api/health` 输出逐字节一致，静态资源与章节接口字节级一致，关系智能接口逐字段一致
（验证脚本：`cd heartflow-c && sh tests/run-all.sh`，7 组回归，含用本地假上游覆盖 `/api/chat` 转发与错误分支、用本地假推理后端覆盖 `/api/tts`，不消耗真实额度；发布前的统一门禁是 `npm run gate`，另含 v2 契约、C/Node 检索与语义一致性、安全冒烟与发布清单）。

另于 2026-11-07 做过一次**真实模型端到端验证**（`heartflow-c/tests/real-e2e.py`，需手动运行）：本机 ChatTTS（CUDA，权重加载 24.55 秒 / 显存 1077 MB）与 Kokoro（CPU）各真实合成一句，均返回有效 24 kHz / 16-bit 单声道 WAV、非静音、未削波；`mimo-v2.6-flash` 真实请求返回非空正文；真实浏览器经 C 服务调用真实上游 12/12 通过（`docs/verification/2026-11-07-browser-e2e-live-C.md`）。该次验证还定位并修复了「请求行未剥离 `?query` 导致前端 JS 模块全 404」的缺陷。详见 `heartflow-c/README.md`「真实模型端到端」与「坑 6」。

前端是纯 Vanilla JS，不依赖 React/Vue 等框架。状态持久化在浏览器 localStorage。
计算与规则层（关系智能、教练评分所需的结构化分析、TTS 文本与音频处理）已下沉到 C 服务端；前端只做渲染与交互。

**语音为什么还留一点 Python**：ChatTTS 依赖 PyTorch/CUDA，没有可用的纯 C 推理 API；Kokoro 虽是 ONNX，走 onnxruntime 的 C API 就要引入 DLL 并复刻 phonemizer，与「单二进制零依赖」冲突。因此 Python 侧只剩「加载模型 + 推理」，C 通过 `format=pcm` 拿 raw float32 后自己做响度归一化与 WAV 封装（8 组信号与 Python 字节级一致）。

### 模型兼容性

HeartFlow 通过本地 `/api/chat` 代理转发请求到上游 LLM 服务。支持两种 API 格式：

- **Responses API**（`LLM_API_MODE=responses`）— OpenAI 新格式
- **Chat Completions**（`LLM_API_MODE=chat_completions`）— 通用兼容格式

已验证的模型服务商：

| 服务商 | Endpoint | 模型 | API Mode |
|--------|----------|------|----------|
| MiMo（默认推荐） | `https://token-plan-cn.xiaomimimo.com/v1/chat/completions` | mimo-v2.5 | chat |
| OpenAI | `https://api.openai.com/v1/responses` | gpt-5.6 | responses |
| DeepSeek | `https://api.deepseek.com/chat/completions` | deepseek-chat | chat |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` | qwen-plus | chat |
| Moonshot/Kimi | `https://api.moonshot.cn/v1/chat/completions` | moonshot-v1-8k | chat |
| GLM | `https://open.bigmodel.cn/api/paas/v4/chat/completions` | glm-4-plus | chat |

### 启动指令

**环境要求：** Windows（服务端出站 HTTPS 使用系统自带的 WinHTTP）。C 版为单文件，
无需 Node.js、npm 或任何运行时依赖；Node.js >= 18 仅在需要用参照实现时才是必需的。

**第一步：配置环境变量**

```powershell
cd E:\一门给年轻人的恋爱成长课\relationship-simulator
copy .env.example .env
notepad .env
```

编辑 `.env`，把 `LLM_API_KEY` 改成你的真实 API Key。以 MiMo 为例：

```dotenv
LLM_ENDPOINT=https://token-plan-cn.xiaomimimo.com/v1/chat/completions
LLM_API_MODE=chat_completions
LLM_MODEL=mimo-v2.5
LLM_API_KEY=sk-你的真实密钥
```

**第二步：启动服务（C 版）**

```powershell
npm start
# 或直接在项目根：heartflow-c\hf.exe serve --port 3000 --root .
```

终端会显示：

```
恋爱模拟器（C 版）已启动: http://localhost:3000
API 代理: POST http://localhost:3000/api/chat
模型: mimo-v2.5
Endpoint: https://token-plan-cn.xiaomimimo.com/v1/chat/completions
API Key: 已配置
静态目录: ...\public
```

没有可用的 `hf.exe` 时先构建：`cd heartflow-c; .\build.sh`（详见 `heartflow-c/README.md`）。

**可选：启动 Node 参照实现**

```powershell
npm run start:node
```

两份实现的行为已对照验证；保留 Node 版是作为可独立核对的参照基准（`heartflow-c/tests/parity.py` 逐字段比对）。质量门禁 `npm run check:circular` 已走 C 版，JS 对照为 `npm run check:circular:js`。前端 JS 不会全面 wasm 化：浏览器仍需 JS 做 DOM 与 wasm 胶水，且计算层已在 C 服务端，重复编一份浏览器 wasm 无收益（实测见 `heartflow-c/.wasm-probe/build.sh`）。

**第三步：打开浏览器**

```
http://localhost:3000
```

**可选操作：**

- 切换模型 — 在左侧面板的 Model 输入框直接输入模型 ID（如 `mimo-v2.5-pro`）
- 切换角色 — 左侧面板"切换女方角色"下拉菜单
- 自定义角色 — 展开"自定义角色"折叠面板，填写后保存
- 导出对话 — 点击顶部"导出"按钮
- 重置对话 — 点击顶部"重置"按钮
- 检查模型连通性 — 点击顶部"检查模型"按钮

### 使用建议

1. **先选对阶段。** 如果你刚加微信，就选"刚加微信后的第一晚"，别跳到"暧昧推进"。阶段决定了 AI 的行为尺度和建议的合理范围。

2. **先发消息再看建议。** 先自己写回复发出去，再看教练评分和 A/B/C 建议。如果每次都先看建议再抄，练的不是你的能力。

3. **用 Preflight 当安全检查。** 发送前点一下"发送前测验"，如果有高风险警告，先改掉再发。

4. **关注短板维度。** 教练评分的四维里，最弱的那个才是你该重点练的。自然度低说明表达生硬，共情低说明没接住对方情绪，边界感低说明推进太快，推进力低说明对话容易断。

5. **长篇模拟当教材读。** `long-simulation/` 里的 10 章对话是完整的关系推进案例。每章的"恋爱大师复盘"是精华 — 它不是在教完美话术，而是在指出每个选择的后果和更好的表达方式。

### 常见问题

**Q: 启动后点"检查模型"报错？**
检查 `.env` 里的 `LLM_API_KEY` 是否填写正确，`LLM_ENDPOINT` 是否和你的服务商匹配。

**Q: 回复很慢？**
默认超时 30 秒。可以换更快的模型（如 `mimo-v2.5` 比 `mimo-v2.5-thinking` 快），或检查网络。

**Q: 可以不用 MiMo 吗？**
可以。任何 OpenAI-compatible 接口都行，改 `.env` 里的 `LLM_ENDPOINT`、`LLM_MODEL`、`LLM_API_MODE` 和 `LLM_API_KEY` 即可。

**Q: 对话数据存在哪里？**
浏览器 localStorage。清除浏览器数据会丢失对话记录。可用"导出"功能备份。

**Q: 需要 `npm install` 吗？**
不需要。项目零外部依赖，纯 Node.js 原生模块运行。
