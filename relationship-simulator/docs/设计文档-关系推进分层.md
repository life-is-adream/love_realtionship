# 设计文档：关系推进分层引擎

> 来源：OnlyFans GFE 代聊漏斗的逆向工程
> 版本：v1.1（2026-10-21）
> 状态：**机制 B 与机制 C 已实施**（详见 §10），机制 A/D 仍为设计稿
> 关联：`核心模块 core/state.js`、`core/stages.js`、`core/investment.js`、`coach/prompts.js`、`core/memory.js`

---

## 1. 结论

GFE 漏斗真正可复用的不是话术，是**三层运营结构**：

| 层 | GFE 的做法 | 本产品的对应物 | 是否可迁移 |
|---|---|---|---|
| 分层 | 按消费能力分 New/Flirt/Buyer/Whale/Expired | 按**可观测投入度**分 L0–L4 | ✅ 可迁移，但变量要换 |
| 建档 | CRM 暗中记录，用来"假装记得" | **用户可见可编辑**的关系档案 | ✅ 可迁移，透明度要反转 |
| 节奏 | 间歇性强化，随机奖励拉留存 | **可预期节奏** + 明确的下次锚点 | ⚠️ 机制可迁移，随机性必须去掉 |

必须反转的一条：**桥接（Bridge）**。GFE 在情绪峰值处插入商品，赚当期转化；本产品应在情绪峰值处**收束**，赚记忆留存。

## 2. 机制 A：五段式的逆向重写

### 2.1 原版结构

```
钩子 Hook → 建档 Qualify → 共鸣 Rapport → 桥接 Bridge → 埋钩 Seed
  换回复      采集信息        制造被理解      转为交易      制造复购
```

第 4 段是整个漏斗的变现点。三种桥（稀缺桥 / 专属桥 / 情绪桥）本质都是「在对方情绪最高的时候要求付出」。

### 2.2 反向结构

```
接触 Contact → 建档 Qualify → 共鸣 Rapport → 落点 Landing → 自然收束 Close
   轻开场        采集信息        制造被理解      情绪到达顶点    主动结束
```

第 4 段从「要求付出」改成「不再索取」。依据是 peak-end rule：一段体验的记忆由**峰值**和**结尾**决定，不由总时长决定。GFE 在峰值换成交易，结尾是付款；反向设计在峰值停住，结尾是"聊得很好"。

### 2.3 落点（Landing）的三种写法

| 类型 | 做法 | 适用场景 | 反面（不要这样） |
|---|---|---|---|
| **承接型** | 只把对方最后一句话接住并加重，不推进任何事 | 对方在倾诉、情绪浓度高 | 接完立刻问"那周末有空吗" |
| **暴露型** | 自己先给一层真实的自我披露，不要求对等回报 | 关系进入 L2 以上 | 给完立刻索取："该你了" |
| **留白型** | 主动结束对话，给下次留一个**无条件的**钩子 | 对话已到自然高点 | 用"明天有惊喜"制造悬念换回复 |

三者的共同点：**都不要求对方即时回应或付出**。这是"投资"与"索取"的分界线，也是本产品与 GFE 的分界线。

### 2.4 与现有 A/B/C 的关系

现有三风格不变，只调整**权重**：

- A（温柔高情商）↔ 承接型落点
- B（幽默风趣）↔ 留白型落点
- C（深入了解）↔ 暴露型落点

当 `investmentLevel ≤ L1` 时，C 应当被降权或替换为 A——向低投入对象连续提出深入问题，是「查户口」的标准形态，而 `prompts.js:36` 已经明令禁止这一点，但当前提示词只给了规则、没给触发条件。

## 3. 机制 B：stage × investment 二维分层

### 3.1 现状缺口

`core/stages.js` 定义了 7 个关系阶段，是**一维**的：它只知道"关系走到哪"，不知道"对方投入多少"。

两者不是一回事。同一阶段（如「暧昧推进」）下，L1（被动回应）和 L4（主动共建）需要完全相反的动作。当前代码无法区分，因为 `prompts.js:31` 的"判断投入程度"是每轮重算的瞬时值，不落库、不进策略。

### 3.2 投入度的可观测代理

**原则：只测量行为，不推断心理。** 这与 `coach/evidence-contract.js` 的契约一致——输出 observations 而非"她喜欢你"。

| 档位 | 名称 | 可观测判据 | 数据来源 |
|---|---|---|---|
| L0 | 观望 | 只回答不提问；单字/表情为主；从不主动开启话题 | 消息长度、问号数、首条发起方 |
| L1 | 回应 | 有问必答，有内容扩展，但不反问 | 消息长度、提问比例 |
| L2 | 参与 | 开始反问、补充细节、接梗、引用上文 | 提问比例、新信息条目数 |
| L3 | 主动 | 主动开话题、主动分享近况、记得上次说过的内容 | 会话首条发起方、跨会话引用 |
| L4 | 共建 | 主动提出见面/共同计划、主动关心你的状态 | 邀约动词、关切句、计划类表述 |

每档输出 `{ level, evidence[], confidence }`。**confidence 为 low 时一律按低一档处理**——宁可低估，不可高估。这条直接对应 `prompts.js:31` 的"不要把礼貌回复误判为暧昧或高投入"。

### 3.3 策略矩阵

`action = f(stage, investmentLevel)`，输出四种动作之一：

| | L0–L1 | L2 | L3–L4 |
|---|---|---|---|
| **前期**（加微信/轻联系） | 观察：只做承接，不推进 | 维持：正常互动，不加码 | 推进：可小步升级 |
| **中期**（首次邀约/约会后） | 后退：降低频率，回到轻联系 | 维持：巩固，不急于升级 | 推进：明确下一步 |
| **后期**（暧昧/表达好感/确定） | 后退：暂停推进，先修复投入 | 观察：不追加投入 | 推进：可明确表达 |

「后退」不是冷处理，是**停止追加投入并降低要求**——这是唯一在低投入下不会造成反感的选项。

### 3.4 代码落点

**新增** `public/modules/core/investment.js`

```js
/**
 * @typedef {Object} InvestmentEstimate
 * @property {0|1|2|3|4} level
 * @property {Array<{signal:string, text:string}>} evidence
 * @property {"high"|"medium"|"low"} confidence
 */
export function estimateInvestment(messages) { /* 纯函数，无副作用 */ }
export function planAction(stage, level) { /* 返回 "observe"|"hold"|"advance"|"retreat" */ }
```

设计约束：
- 纯函数，输入 messages，输出 estimate，不读 localStorage、不读 state（便于单测，参照 `coach/analysis-result.js` 的 dependency-free 风格）
- 至少 5 条证据才允许 `confidence: high`
- 仅在 `messages.length >= 10` 时计算，否则返回 `confidence: low`

**修改** `core/config.js` → `defaultState` 增加：

```js
relationshipTier: { level: 0, confidence: "low", evidence: [], updatedAt: null }
```

**修改** `core/state.js` → `normalizeState` 增加一行容错（参照现有 `normalizeMistakes` 的写法）：

```js
normalized.relationshipTier = normalizeRelationshipTier(normalized.relationshipTier);
```

**修改** `coach/prompts.js` → `buildSystemPrompt` 增加一段读取 `memory._tierInjection`（与既有 `_enhancedInjection` 同一条注入链路，避免改动 `api-client.js`）：

```js
  if (memory._tierInjection) {
    parts.push(memory._tierInjection);
    parts.push("");
  }
```

注入内容由 `buildTierPromptLine(tier, stage)` 生成，形如：

```
- 对方投入度：L2 参与（置信度 medium，样本 12 条）。本轮策略：hold（维持，正常互动，不加码）。
- 依据仅为可观察行为（对方共 6 条消息；提问 2/6 条；平均长度 18 字），不得据此推断她的内心或给出好感概率。
```

改动量：约 6 行。

## 4. 机制 C：记忆明示化

### 4.1 现状

`core/memory.js`（575 行）已经能提取：
- `memoryTimeline` — 事件时间线（上限 100）
- `conversationSummaries` — 对话摘要（上限 20）
- `learnedPreferences` — 偏好/风险区/优势
- `interactionHistory` — 轮次、常见话题、沟通模式

但这些只通过 `_enhancedInjection` 注入 prompt，**用户看不到、也不能改**。

### 4.2 为什么必须反转

GFE 的记忆是**隐藏的**——它存在的意义是让 chatter 跨班次不穿帮，即"用一个假身份维持连续性的幻觉"。

明示的记忆是**可见的**——它存在的意义是让用户知道系统掌握了什么、并能纠正。两者技术同源，产品含义完全相反：

| | 隐藏记忆（GFE） | 明示记忆（本产品） |
|---|---|---|
| 目的 | 维持身份幻觉 | 提供可修正的上下文 |
| 用户能否查看 | 否 | 是 |
| 用户能否删除 | 否 | 是 |
| 出错时 | 无法纠正，只能继续演 | 一键修正，记忆更新 |
| 合规属性 | 风险项 | 优势项 |

### 4.3 落地

新增 `public/modules/render/render-memory-panel.js`，把 `memoryTimeline` 与 `conversationSummaries` 呈现为「关系档案」：

- 按时间倒序，每条显示：时间、事件、来源（自动提取 / 用户补充）
- 每条右侧提供「修改」「删除」
- 顶部显示 consent 状态，与 `core/privacy.js` 的现有授权流程共用
- 删除后同步更新 `relationshipIntelligence.memory`（`intelligence/state.js` 已有 consent gate，无需新建机制）

这一项的额外收益：它把"我记得你说过"从**不可验证的宣称**变成**可检查的能力**，这是真正的产品差异化点。

## 5. 机制 D：节奏与召回

### 5.1 对比

| | GFE | 本产品 |
|---|---|---|
| 唤醒方式 | 随机奖励（忽冷忽热最上瘾） | 固定节奏 + 进度可见 |
| 用户感受 | 焦虑驱动（怕失去） | 掌控感驱动（看得见成长） |
| 长期结果 | 留存高但信任低，退订即断裂 | 留存慢但信任高，可转介绍 |

间歇性强化是整套 GFE 体系里最"有效"也最不道德的一条：它借用了老虎机的机制。**移除它不会显著降低留存，但会显著降低用户事后的怨恨。**

### 5.2 落地

`core/learning-state.js` 已有 `dailyTasks`、`growthSnapshots`、`events` 三个容器，可直接承载，无需新数据结构：

- 会话结束触发：写入一条 `growthSnapshot`（本次练习的一个具体进步 + 一个具体待改进）
- 下次锚点：`dailyTasks` 增加一条**具体可执行**的练习，不使用"明天有惊喜"这类悬念
- 不做推送提醒的紧迫感设计；提醒文案不带"限时""错过"

## 7. 红线清单

以下五条来自 GFE 分析中被证明"有效但不可用"的做法，本产品明确不做：

1. **不输出"她喜欢你"的概率** — 已在 `prompts.js:32` 约束，新增 tier 后必须继续遵守，tier 只描述行为不描述心理
2. **不做随机奖励式唤醒** — 见 §5
3. **不做隐藏记忆** — 见 §4，记忆必须用户可见可删
4. **不做"解锁才给"的付费墙** — 付费点放在体验升级，不放在关系断点
5. **不做身份伪装** — AI 身份默认可识别。参照 EU AI Act Art.50（2026-08-02 生效）与纽约 S-3008C：交互式 AI 须在会话开始时表明非人类身份

## 8. 落地顺序与验收

### 第 1 步：`investment.js` + 单测

- 纯函数，不接入 UI，不改任何现有行为
- 单测覆盖：空消息、单轮、高低投入各一例、confidence 降级逻辑
- **验收**：`node --test test/*.mjs` 全绿（当前基线 769/769），新增用例 ≥ 8 条
- **验收**：对 3 段真实对话（低/中/高投入）的判定与人工标注一致，误差 ≤ 1 档

### 第 2 步：注入 prompt

- 只改 `prompts.js` 与 `state.js`，不动 UI
- **验收**：同一段对话，开启 tier 前后各生成 5 组 A/B/C；低投入场景下 C（深入了解）出现率显著下降
- **验收**：`retreat` 策略下，A/B/C 中邀约类表述出现次数 = 0

### 第 3 步：记忆面板

- 新增 `render-memory-panel.js`，接现有 consent 流程
- **验收**：删除一条记忆后，下一次请求的 prompt 中不再出现该条
- **验收**：未授权状态下，面板不显示任何记忆内容

## 9. 一句话总结

GFE 把那套东西用来**制造一个不存在的连续人格**；本产品把同一套结构用来**建立一个可检查的真实记录**。技术栈几乎一样，差别只在"记忆对谁可见"和"桥接要不要收钱"这两处。

### 关键实现决策

1. **tier 只派生、不接受外部注入。** `persistState` 每次用 `deriveRelationshipTier(messages, previous)` 覆盖，任何伪造的高档位都会被消息实际内容冲掉（`test/memory-panel.test.mjs` 有专门用例锁定）。
2. **置信度不足降一档**已内置于 `estimateInvestment`，不是提示词层的软约束。
3. **删除可见记忆必须改变生成结果**，否则面板是装饰。因此 `buildMemoryInjection` 增加了时间线注入；删掉的条目不会再出现在 prompt 中。
4. **未授权时不渲染任何记忆内容**。`core/state.js` 原本就会在关闭授权时删除 `_enhanced`，面板只显示 gate。
