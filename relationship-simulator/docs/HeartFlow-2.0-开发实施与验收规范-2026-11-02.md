# HeartFlow 2.0 开发实施与验收规范
版本：v1.0 日期：2026-11-02 适用对象：Qoder、Codex、其他执行 Agent、项目维护者 依据：《HeartFlow 技术与项目现状（供外部 AI 分析）· 2026-11-02》 文档性质：待实施的软件需求规格（SRS）+ 架构决策（ADR）+ 开发任务分解（WBS）+ 验收测试协议（ATP） 状态：设计方案；不宣称已修改仓库，也不宣称达到目标指标。
# 0. 总则与实施边界
## 0.1 产品定位
HeartFlow 是本地、单用户、中文恋爱沟通成长练习工具。核心闭环为「模拟角色对话 → 证据驱动教练分析 → A/B/C 不同沟通动作 → 教材训练 → 复盘 → 下次训练」。允许独立的陪伴演出模式，但它不取代现实关系，虚构情境不能作为真实关系判断的证据。
对标 CyberChat 的用户可体验的能力，不以复制其未知代码、私有 API、隐藏模型或视觉素材为目标。CyberChat 的具体内部技术未经证实，禁止把推测写成已确认事实。
## 0.2 不可突破的技术约束
• 前端：原生 ESM、原生 HTML/CSS、零构建、零运行时外部依赖；保留既有目录分层。
• 后端：Node.js ≥18，现有 server/ 内置模块为主；保留单一本地 LLM/TTS/search 代理。
• 持久化：保留 localStorage（heartflow-state 等既有键）；不引入 SQL/NoSQL、向量库、Redis、消息队列、任何服务端持久化。
• 不新增微服务、Docker、用户体系、鉴权体系、计费或多租户能力；已存在的本地 Python TTS sidecar 保留。
• 所有前端状态写入经 mutate()；日期键走 shanghaiDate()；沿用现有 escapeHtml、R1–R7 和 request-scope 契约。
• 不允许重置、丢弃或覆盖用户未提交 WIP；禁止执行 git checkout/restore/reset/clean 等会破坏工作区的操作。任何改动先审阅 git status 与目标文件 diff。
• 付费模型测评默认 dry-run，只有用户对具体次数及预算同意后才能执行；不得通过 UI 自动触发批量付费评测。
• 禁止无证据地断言他人的心理、喜好概率或隐秘意图；禁止欺骗、骚扰、嫉妒测试、虚假稀缺、冷处理惩罚、性压力。
## 0.3 真实基线（来自项目摘要，未在本环境复测）
• 87 个前端 JS、14 个后端模块、84 个测试文件、922 项现有测试通过；循环依赖与约定违规 0。
• MiMo mimo-v2.6-flash；角色通道 HER_LANE 关闭思考、预算 200 tokens；教练通道 COACH_LANE 关闭思考、JSON 模式。
• 角色首次可见时间报告为 1.2–6.7 秒，偶发长尾 17–24 秒；教练非流式完成 P50 约 24.2 秒，某次最慢 49.1 秒；评测样本不足，不能据此计算稳定 P95。
• 现有上游 stream:false、MAX_ATTEMPTS=2、UPSTREAM_TIMEOUT_MS=120s，严重延迟仍可能发生。
• 已知高优先级缺陷：教练生成用户未提供的地点/时间；记忆没有来源追踪、冲突取代与 real/simulation 隔离。
• 另有 trainingMode 二元回退散落 6 处，多角色、主动消息、世界书、分支回放未完成。
# 1. 产品目标及验收范围
## 1.1 核心目标（必须）
G1·快速：角色短文本对话完整可见 P95 ≤ 6.0 秒，首个有效正文 P95 ≤ 2.0 秒（见 §2 的严格计时与样本协议）。教练独立异步展示，不计入角色 6 秒目标；不可把“打字动画开始”“加载骨架”或本地预置回复算作模型首字。
G2·可信：教练 A/B/C 的关键事实断言可映射到现有会话证据；不把候选提议写成已经发生的约定；对未知事实显式保留未知。
G3·会记得：结构化长期记忆支持新增、更新、取代、来源追溯、删除、现实与模拟作用域隔离；追踪尚未完成的约定 openLoops。
G4·像一个连续的角色：人设稳定，了解实际经过的时间、当前情境、剧情事件，但不凭空知道尚未获知的信息；支持独立“训练/陪伴”策略。
G5·有训练收益：179 课参与个性化教学；训练建议可以关联某课、某个可观察的技能弱项，能够进行相同场景的分支回放。
G6·工程不倒退：保留旧档案、旧角色卡、当前所有可用功能；避免重复消息、错会话消息、请求取消后的晚到提交。
## 1.2 版本承诺边界
• MVP（本轮必须交付）：P0 工作区安全、P1 事实约束、P2 极速回复链、P3 结构化记忆。
• V2（下一轮）：P4 角色连续性和双模式、P5 训练闭环。
• 扩展（明确非本轮验收）：图片/视频生成、多人群聊、社交社区、多人账号、在线部署、SillyTavern 全兼容、全量向量 RAG。
• 不承诺：第三方 MiMo 在任意网络波动、任意长文本和任意时刻 100% 低于 6 秒；复杂教练必须在 6 秒内完成；反推出 CyberChat 的私有内部实现。
• **反向锚点（2026-11-03 据 CyberChat 只读客户端分析增补，明确不做）**：
  — 亲密度/情绪数值化的留存钩子（对方客户端以 `qinmi` 扣费、`update_emo` 每轮携带情绪态）。本项目成长模式禁用情感数值，这条诱惑真实存在，写下来当反面标尺。
  — 服务端会话持久化与聊天正文入库（对方 `chat_log_insert.php` 连 token 计数一起上报）。本项目坚持 localStorage、零服务端存储。
  — 同步阻塞式模型调用（对方 `post_v3.php` 用同步 `$.ajax`）。这恰好是 P2 流式通道要拉开的差距，不是要对齐的写法。
  — Service Worker 缓存。本地 http 服务无此需求，且本轮已实测踩到缓存副本坑（同一模块被加载成两份，读到过期实现）。
  — 百万字节单文件前端（对方 `script.js` 约 1.06 MB）。本项目 104 模块、循环依赖 0、R1–R7 违规 0 是既有优势，不为「功能对齐」稀释。
  — 社区/品牌号/圈子/动态/直播/合影/声音克隆/充值等社交与多租户能力（对方 194 个路径中的大部分）。
  口径提醒：以上均来自**静态客户端证据**（路径名与字段名），未验证接口可用或运行时行为，只用于方向判断与边界确证，不得当作对手已实现功能的结论，也不得据此调整本项目验收指标。
## 1.3 交付物
每阶段必须交付变更文件、测试、兼容说明、验收证据（命令及输出、日志统计、失败样例）、回退方式；不允许只给截图或仅有 Prompt 设计稿。
# 2. 延迟 SLO：定义、测量与降级
## 2.1 可测口径
固定样本集合：短角色回复：中文单用户/单角色的日常问答；输入 15–120 汉字；角色期望生成 1–3 个气泡、总计 20–120 汉字；不触发 TTS、联网搜索、图片生成、深度教练同步阻塞。单独维护中长文本与复杂场景集合，不把它们混入短回复 SLO。
全部时间使用客户端 performance.now()（相对单调时间）：
• t0：用户确认发送操作发生、应用接受消息的时间；
• t1：收到首个通过过滤的非空正文 delta.content 并完成首字符可见 DOM 更新；
• t2：完整正文被呈现、模型结束标记已收到、分气泡结构最终确定（不等待故意添加的打字动画）；
• TTFV=t1−t0；TTFC=t2−t0；同时记录 upstream 首字、首包、总时间、输入输出 tokens、缓存命中（若可得）。
主指标：本轮成功生成且 TTFC≤6000ms 的样本数/全部合格发送样本数（含超时/失败在分母）≥95%。辅助指标：合格发送的完整可见时间最近秩 P95≤6000ms、TTFV 最近秩 P95≤2000ms；超时失败不得从分母删除来美化 SLO。缓存冷/热分别报告；禁止用纯 Mock 指标证明第三方真实 API 的性能。
## 2.2 运行条件及样本量
• 本地 Node 代理、固定网络环境和固定模型版本；采样时保留网络与服务状态信息；进行 A/B 时同样输入集、会话历史规模和随机化顺序。
• 免费 Mock/网络故障测试至少 200 次；真实 MiMo 性能发布验收须单独获批 40 个有效请求，默认不执行。40 次用最近秩 P95 即排序第 38 个数据点；主 SLO 相当于至多 2 次不能在 6 秒内成功完成。此统计属于工程发布门槛，不宣称反映所有时段/地区的真实总体 P95；若预算不足只出“尚未验证”。
• 另选 12–20 个有代表性的真实模型行为用例进行低成本质量回归，每次执行前显示精确请求次数、上限 token 及估算费用，经 --yes 才发起。
• 每个性能报告输出 n、请求成功数、超时数、P50/P90/P95、最大值、TTFV、TTFC、tokens、模型及参数、日期、采样方法和原始脱敏数据。
## 2.3 超时与回退
• 第 6 秒未完成：UI 可以提示“仍在生成”，但这次计为未达 6 秒 SLO；不得显示假装模型已回答的模板。
• 第 8 秒仍无完整结果（初始实验阈值，可配置）：提供继续等待/取消的交互，不自动盲目重试产生第二次付费；保留尚未完成的草稿状态，但不得作为已完成的角色消息提交。
• 错误、主动取消、切换会话：通过 AbortController 中断本轮网络，利用 createRequestScope 检查当前票据，取消或过期结果不进入正式会话；随后重试只能在明确操作下进行。
• 角色回答成功后异步启动教练；教练超时仅影响教练面板，不回滚已完成角色回复。
• 记录 provider_timeout、http_error、cancelled、stale、parse_error 等明确状态。
# 3. 目标技术架构
Browser / ESM
  app.js
    ├─ request-scope（会话、请求票据、取消）
    ├─ Fast Context Builder（角色卡+有限近期消息+相关记忆）
    ├─ Her Lane → POST /api/chat [stream:true] → Node SSE gateway → MiMo
    │                  ↓ 仅转发经过白名单过滤的正文
    │             流式 DOM → 最终一次 mutate() 提交 her reply
    └─ Coach Lane（her reply 完成后独立启动）
                → 已知事实表 + 既有 investment 结果 + 课程检索
                → POST /api/chat [stream:false, json_object]
                → 回复计划与事实审计 → A/B/C 显示
                         ↓
                后置 Memory Extraction / Summary（无服务端持久化）
                         ↓
                前端 mutate() → localStorage heartflow-state
Offline/Optional: ChatTTS & Kokoro voice sidecar；不阻塞文字路径
不改的部分：Node 本地单代理、MiMo Provider、浏览器持久化、现有应用布局、179 课资源、测试运行器。要变的部分：上游 SSE 解析与转发、前端流式消费、角色上下文预算、教练事实约束、结构化记忆。
## 3.1 Fast Lane 与 Coach Lane 服务契约
角色通道配置建议初值：mimo-v2.6-flash；thinking.type=disabled；stream=true；max_completion_tokens=160–200（先维持 200 作基准，再 A/B 160）；不生成 JSON，不添加教练推理。不把参数错误当成模型故障；先以官方文档和 1 次手动授权的真实调用核实兼容。
教练通道保持独立：thinking.type=disabled、response_format=json_object、非流式（先不改其网络协议）；最大输出预算通过测量设置，而不是直接保留 4096 全额生成。建议拆成“快速核心建议”与“按需深度分析”，先上线质量不下降的最小字段集。
关键实现：SSE 服务端解析器只接受 choices[].delta.content 中的字符串；任何 reasoning_content、tool_calls、未知字段都禁止传入可渲染正文。流式完整帧可能跨 TCP chunk，必须缓存后按 SSE 事件边界解析；流中途中止要处理 abort、EOF、[DONE]、错误帧和无完整帧，不能每个 chunk 直接 JSON.parse。
## 3.2 API 协议
现有 /api/chat 必须向后兼容。可选增加 stream:true 分支（或并行 /api/chat/stream，实际以现有 server/request-handler.js 结构最少修改为准）。
请求（概念契约，具体字段须映射现有 buildHerMessages）：
{
  "messages": [{"role":"system","content":"..."},{"role":"user","content":"..."}],
  "model":"mimo-v2.6-flash",
  "stream":true,
  "thinking":{"type":"disabled"},
  "max_completion_tokens":200,
  "requestId":"local-generated-uuid",
  "lane":"her"
}
浏览器侧 SSE 事件（本地代理自定义，不要求 MiMo 原样输出）：
event: message.start
data: {"requestId":"..."}
event: message.delta
data: {"requestId":"...","text":"你好"}
event: message.end
data: {"requestId":"...","finishReason":"stop"}
允许 message.error，携带白名单错误代码与易读说明（不能传密钥、原始敏感 prompt、供应商内部堆栈）。请求 ID 不作用户鉴权；当前项目只有本地单用户。SSE 响应设置 Cache-Control: no-cache，适当刷新输出并处理浏览器断连，确保 Node 不悬挂。
## 3.3 并发与消息提交
• 前端发送时生成 mid 与 requestId；同一次用户操作重入只接受一个请求。
• 流式文本只进“临时消息缓冲区”，在 [DONE] 且 isCurrent() 成功后一次 mutate() 提交，保存该角色 mid；服务端不持久化会话。
• 先提交她的完整回复，再以新 dialogue-coach 票据启动教练，避免旧的上下文快照误判教练过期。
• 不自动同时让多个模型写同一会话；不同会话请求互不污染；取消不能吞掉提交阶段的真实异常。

# 5. P1：Grounded Reply / 教练事实审计（最高优先级）
## 5.1 问题定义
教练将“建议新提出的时间地点”误写成“已经约定的事实”，违反产品底线。这个问题同时是 Prompt 设计、数据表示和输出校验问题，必须综合修复。
## 5.2 数据契约
EvidenceLedger 只从已保存的用户/角色发言和明确输入中构建（kind=observed|user_asserted|character_asserted|simulation_event，sourceMessageIds、scope、confidence）；不得把教练自由生成文本重新写成事实。
ReplyOption 结构：
{
  "id":"A",
  "action":"ACKNOWLEDGE_AND_ANSWER",
  "text":"那周六下午两点可以吗？",
  "assertedFacts":[],
  "proposals":[{"kind":"time","value":"周六下午两点"}],
  "sourceMessageIds":[],
  "needsUserFill":false
}
核心区分：assertedFacts 是已发生/已知事实；proposals 是新建议、询问或假设。虚构角色可以在明确模拟剧情里创作生活细节，但教练不得把它们冒充用户提供的现实资料。
## 5.3 执行顺序
1. 新建纯函数 evidence-ledger.js（建议目录 public/modules/coach/），提取或组合可溯源事实。
2. 调整 buildCoachSystemPrompt：禁止无证据扩写历史约定，明确 assertedFacts/proposals、未知量、A/B/C 三种动作。
3. 新建 reply-grounding.js 校验 schema、事实来源、时间地点断言，以及 A/B/C 差异性；词面检测仅作保守的高风险提示，不假装能证明所有自然语言语义。
4. 对未能安全判定的句子走“用户待确认”或骨架式替代；不得悄悄改写成肯定事实；不允许为了合格率直接大量屏蔽有用建议。**（2026-11-03 实测补充第二子类）** 教练还会替用户新增他自己没说过的处境 —— 她只说「周四要交读书报告，你呢」，教练写「我这边也快了，明天要交一个课程作业」。这类句子既无回忆框架也无征询框架，容易被当成合法新提议放行，而它的后果最重：**照抄就是用户对真实的人撒谎**。处置方式与假日程不同：第一人称 + 台账里没有的实体 + 无决策/征询框架 ⇒ **只标注、不改写原文**（分不清「陈述处境」与「陈述新提议」时，误杀一条好建议的代价低于漏掉一句假话）。标注必须落到具体那一条建议上，只给一句汇总提示不够 —— 用户会照着另一条把假话发出去。标注再加一道个人处境闸门：句子确实交代了自己的事（忙/有空/加班/作业/一般…）才标，玩笑与无语义主张的措辞不标 —— 提醒被滥发之后用户会整体无视它。
5. 保留已有 isUsableModelReplyOptions、buildReplyOptionsForHer 的有效能力，添加回归测试。
6. **（2026-11-03 人工盲评补充第三、第四子类，来自真实抽样的放行项）**
   - **虚构地址/线路/路程 ⇒ 拦截。** 用户只说「上次你说想吃日料」，教练写「那家在天河城那边，坐地铁三号线到体育西路站走五分钟就到」。中文地名是开放集，靠地点词表补不完（当时词表拦不住，三条全漏）。规则改为判**框架**：`在X那边/附近`、`地铁N号线`、`到X站`、`走N分钟就到` 出现台账外实体即按捏造拦截；提议豁免只留给带征询痕迹或小句有主语的写法（「我们在天河城那边见可以吗」合法）。第一人称自己的位置陈述只标注不拦。时间编错了对方会当场纠正，地址编错了用户会照着出门 —— 后者是现实世界的错误。
   - **替用户补全所指对象的内容属性 ⇒ 标注。** 用户说「最近有部纪录片挺火」，没说是哪部、讲什么；教练写「讲城市里普通人的生活变迁那种」。这类句子**没有任何时间地点实体**，前述实体规则全部看不见，按「谓语形态（讲/偏…的/就是那种/题材/类型）+ 与台账零三字重合」判定，只标注不改原文；用户自己说过的内容被复述时不标。
   - **验收证据必须分三态呈现。** 拦截、标注、放行要分别在报告里计数并逐条标明。把「标注」印成「通过」，等于让读报告的人以为 23 条干净，而实际 6 条早已被审计器标 —— 与「0 分母报成 0%」是同一类失效。

验收：固定 50 条负例+20 条正例 免费离线用例：负例中关键人物/地点/时间/约定“捏造为既成事实”0 次；正例中新提出的时间地点至少 95% 不被错误拦截；3 个回复必须存在三个不同动作，**问句结尾硬门槛 ≤2 条、≤1 条作为提示词引导目标**（2026-11-03 实测修订：原「≤1」硬门槛在 12 轮真实抽样里判死了 2 轮动作分布本身合格的输出，问句数量不是动作互斥的好代理指标；本地模板仍自检 ≤1）；角色明确提问时 A 回答其问题（若事实未知则明说缺少资料或提供可填骨架）。再做小规模获批真实模型抽样 + 人工盲评，人工发现高风险错误则阻断发布。
# 6. P2：6 秒快速角色回复链

## 7.1 最小数据模型
{
  "schemaVersion":2,
  "memories":[{
    "id":"m-001","kind":"fact","subject":"user",
    "content":"用户喜欢摄影展","scope":"real",
    "importance":4,"confidence":1,
    "sourceMessageIds":["mid-123"],
    "status":"active","supersededBy":null,

  }],
  "openLoops":[{

    "status":"open","scope":"simulation",

  }],
  "summaries":[{
    "id":"s-001","conversationId":"c-01",
    "throughTurn":20,"version":1,"content":"..."
  }]
}
## 7.2 处理流程
1. 稳定消息 ID：为新消息生成 mid；迁移旧消息时生成稳定 ID，一次迁移后再次读取不改变。
2. 保留兼容：旧 background/interests/boundaries/memoryTimeline/conversationSummaries 只读迁移；迁移失败保留原始字符串到既有 quarantine，不用空默认值覆盖旧数据。旧条目如不能证明是现实或模拟，应标为 unknown 或 unverified 并禁止进入现实事实注入，不能默认标成 real。
3. 提取：只记录明确的用户/角色已说事实，输出 ADD/UPDATE/SUPERSEDE/NOOP；身份、时间、作用域与来源不可为空；低置信度待确认而不是自动写入。
4. 更新：冲突优先标记旧事实 superseded，保留历史，不直接粗暴覆盖；删除某条消息时清理/失效依赖其来源的自动记忆。
5. 检索：先按 scope + participant + status 过滤，再按关键词命中、重要性、时间和最近使用排序，限制 3–6 条以及总 token 预算。禁止 real/simulation 跨范围调用。
6. 摘要：每 N 轮对未摘要部分做增量摘要，(conversationId, throughTurn) 为幂等键，不覆盖较新版本；摘要不代替事实库。**同时必须提供用户主动通道**：手动固化当前摘要（`source:"user"`）与立即触发一次摘要。理由是「哪段对话值得记」用户比模型清楚，本地单用户工具没有理由把这件事全交给轮次计数。
7. 开放事项：openLoops 必须有来源和状态；提起时以自然问题形式表达，不擅自认定约定已完成。
8. 隐私与注入：历史数据作为引用材料，而非新的 system 指令；转发外部模型前复用既有脱敏；保留用户手动编辑/删除能力。
## 7.3 验收
• 100 条固定事实样本：可检索关键事实召回≥90%，返回的事实来源可追踪 100%。
• 50 条冲突/更正用例：旧信息被取代后，正式注入不得再优先引用旧版本；有据可查且用户可撤销。
• 50 条 real/simulation 隔离用例：0 次跨作用域注入；未经同意不得保存为现实关系证据。
• 30 条 openLoops：≥90% 正确跟进/关闭，不虚构完成状态。
• 旧存储迁移：重复加载结果相同（幂等）；遇损坏档案不丢原始数据；现有存储键与 UI 可用性不退化。
• 以上全部可先用免费固定 fixture/Mock 完成；涉及自然语义提取时再用预算批准的小样本验证。
# 8. P4：角色连续性、时间与双模式
## 8.1 角色状态
推荐四槽：persona（身份规则）/ worldState（共享剧情）/ roleKnowledge（此角色已知事实）/ openLoops（待续事件）；另外保留可配置 authorNote、worldBook 简化功能。worldState 不等于每个角色都知道的内容。
## 8.2 双模式
trainingMode 统一解析为 anti、companion、pua_recognition（仅“识别与防御”，非教授操控）；pua/anti 值需通过显式迁移表映射，不能默认为 anti。建议产品对用户显示为“反操控成长”“陪伴演出”“操控识别与防御”，与内部枚举解耦。
• 成长模式：真实沟通证据、反证、风险、边界、训练建议；不使用情感数值或心理猜测。
• 陪伴模式：更自然的对话风格、约会场景、开放剧情、角色主动话题；角色是模拟人物，不用操纵性机制诱导用户留存。
• 共同底线：不鼓励欺骗/骚扰/跟踪/冷暴力/嫉妒测试；在“陪伴”里同样不声称 AI 是现实真人，不把虚构事件写为现实证据。
## 8.3 统一关系引擎
保留已有 investment.js 对可观察行为的分析；服务端关系 runtime 不重新估算“对方内心”，而是只接受分析结果、当前阶段、用户明确目标和风险约束，给出 ADVANCE / MAINTAIN / OBSERVE / DE_ESCALATE / EXIT。对既有 observe/hold/advance/retreat 做显式语义映射，禁止从词面推断直接替换；历史记录保留原枚举版本及迁移后结果。
## 8.4 验收
• 现有 6 处二元回退全部收敛到一个统一解析函数；旧状态迁移不可导致模式意外切换。
• 角色 50 轮连续性测试：设定事实、场景地点、世界时间不出现重大互斥矛盾；关键角色知识隔离测试 30 条：0 次引用未获知事实。
• 时间感知：shanghaiDate() 仍为存储日期键唯一来源；“昨晚/明天/过了三天”取自实际时间与事件日志，遇无时间戳的不自作推断。
• 关系引擎在固定输入下输出确定；无“喜欢概率”；反操控规则所有模式一致。
• worldBook 条目按触发词、优先级和 token 预算注入，无法递归触发无限扩增；有循环终止测试。
## 8.5 陪伴模式的多通道演出层（2026-11-03 增补）
参照同类产品的聊天呈现，把一轮输出拆成可独立开关的通道。经用户决策，边界如下：
• **只进陪伴模式**。成长/识别模式保持单通道气泡 + 教练 A/B/C：那两类模式的产物必须是「真会发出去的微信文本」，掺入旁白会让建议失去可发送性，并架空 P1 的事实审计对象。
• **旁白只由她输出**。用户输入始终是真实会发送的话，不允许用户写第三人称动作叙述；否则用户侧不再是沟通练习，退化为语C 写作。
• 通道清单（localStorage 键 `heartflow-chat-prefs`，逐通道布尔，默认全关）：`innerMonologue`（角色内心）、`actions`（角色行为动作）、`timestamps`（时间戳）、`sceneBlock`（场景状态块：在哪、谁在做什么）。渲染层按 prefs 过滤，不改数据模型。
• 内心独白必须显式标注为**作者虚构的旁白**，不得表述为「她在想什么」的事实；不得进入 EvidenceLedger，不得作为现实关系判断的证据。这是 §0.2「禁止无证据断言他人心理」在演出层的落地方式。
• 打开任一通道都会增加她的输出量，因此必须与 P2 的 6 秒 SLO 分开计量：多通道轮次不计入短回复 SLO 样本集（见 §2.1 的样本隔离要求）。
• 行为动作通道与现有质量判据冲突：`her_natural` 目前把「无括号动作」当作像真人的条件之一，评测必须改为 prefs 感知，否则会自己给自己判不合格。

说明：A-05 是网络和供应商相关的“性能实测门槛”。它与 A-04 的 Mock 稳定性不同；即使 A-04 合格，也不能把 A-05 标为通过。如果用户未批准真实 API 评测，A-05 状态必须是“未测”，不是“通过”；其他功能仍可作为“功能就绪、性能待验收”交付，不得冠以“6 秒已达成”的版本声明。A-03 的 0 漏检只针对构造的明确负例，不是所有开放式语言生成绝对无幻觉的承诺。

## 12.2 最小真实评测授权机制
任何脚本在连接真实模型前必须输出：目标模型、测试集版本、请求上限、单请求 token 上限、预估费用/上限费用、日志存放位置。缺少 --yes 自动中止。预算估算参考当时官方计价与本地历史统计，必须标明“不保证”。超限立即终止；成本估算不能虚构一个固定单价。
## 12.3 保持统计诚实
• 行为评测 n=5 只可称“冒烟测试”，不能报告为 95% 可靠性证明。
• 同源 LLM 裁判仅做低成本问题筛查；质量发布门槛需人工核对至少一部分样例，并保存匿名化判定说明。
• 报告所有失败、超时、解析异常，不能只保留成功样本。
• 性能 A/B 使用相同输入、相同网络条件下交错运行，写明样本和变动参数；拒绝凭“改 Prompt 应该更快”直接宣布成功。
# 13. 安全、数据兼容和回滚
1. localStorage 数据结构引入 schemaVersion=2；迁移只增量转换，原数据损坏时沿用已有 quarantine 机制，禁止默认态直接覆盖用户数据。
2. 角色消息/分析结果二阶段提交：她的有效回复已经持久化后，教练失败不撤销她的回复；后置记忆任务失败不抹掉历史聊天。
3. 持久化 mid、requestId、分析任务状态应有稳定生命周期；重试不得重复追加消息，异步旧请求不得写入新会话。
4. SSE 中绝不渲染或转储模型内部 reasoning_content；若将完整调试帧留在本地文件，应默认关闭且只可在脱敏调试模式开启。
5. 使用现有 privacy.js 清洗模型出站数据；但脱敏本身不能保证绝对匿名，敏感材料输入仍需用户谨慎。
6. 如果模型成本、延迟或质量门槛失败，使用可配置的旧非流式路径进行功能回退；不回滚用户数据、不更改旧档案为不兼容结构。
7. 对每个新能力配置 featureFlags（至少 fastStream, groundedReplies, memoryV2, companionMode），便于局部关闭，而不是靠删除代码回退。

# 15. 给 Qoder / Codex 的直接执行指令
请按照本规范从 P0 → P1 → P2 → P3 → P4 → P5 顺序开发；每次只完成一个阶段。先逐文件查看当前 Git 差异与未提交 WIP，禁止任何恢复、清理或重置命令；执行当前 npm test 建立基线并报告。任何 P0/P1/P2 关键门槛未通过，禁止继续叠加高级功能。坚持原生 ESM + Node 零外部依赖 + localStorage，不引入数据库、前端框架或微服务。对于已有 API/模块，先阅读生产调用点与现有行为测试再增量修改。每个阶段提交“改动摘要、文件清单、测试命令与结果、已知限制、数据兼容、是否需要付费实测及预算”，不声称未执行的测试已通过。真实 MiMo 评测必须先输出 dry-run 与成本估计、得到用户批准后再使用 --yes。如遇任何 WIP 冲突、旧状态迁移风险或外部调用权限问题，停止危险操作并说明具体阻断点。
# 16. 版本目标与比较结论
本规范交付之后，HeartFlow 应成为“快速响应、有来源的教练建议、可追溯的长期记忆、连贯角色、可定向练习的本地恋爱沟通训练系统”。这是一组待验收目标，不是已经实现的功能。
与 CyberChat 的比较只涉及可被观察和复测的同类用户体验：短回复速度、连续 50 轮人格一致、事实/记忆正确性、主动事件、角色卡便利性和多模态体验。不能用第三方网站未公开的内部架构作为本项目验收标准。如果要比较两者“还有多少差距”，必须额外做相同内容的授权黑盒用户体验测试；在此之前不提供虚假的总完成率。
