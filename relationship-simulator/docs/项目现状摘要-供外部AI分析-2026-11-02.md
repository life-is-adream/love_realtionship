## 1. 产品定位与硬约束

- **本地部署、单人自用**的中文恋爱成长教育应用。**明确不考虑**：多用户、鉴权、多租户隔离、限流、计费、横向扩展、备份、容器化、CI/CD。
- 取向是**证据驱动的教练**，不是陪伴机器人。非协商规则见 `E:\一门给年轻人的恋爱成长课\.agents\skills\relationship-coach-cn\SKILL.md`：
  - 默认不假设性别/性取向/城市/学历/经济条件
  - 不使用"她的隐藏意图 / 你的隐藏目标"框架；只输出可观察事实、信号、假设、支持证据、反证、未知、置信度、最小风险行动
  - 不输出未经校准的喜欢概率、匹配度百分比
  - 关系决策只能是 `ADVANCE / MAINTAIN / OBSERVE / DE_ESCALATE / EXIT`
  - 不提供欺骗、骚扰、跟踪、性压力、冷处理惩罚、嫉妒测试、虚假稀缺等方案
- 已确立的产品分档决定（用户选定）：**双档并存**——训练模式选「反 PUA」时克制，选「陪伴」时放开暧昧演出；但不用欲擒故纵/虚假稀缺/嫉妒测试作为机制。

### 2.2 代理行为

- 上游超时 **120s**（`server/llmProxy.js:18`）——大 prompt 下教练 JSON 实测 40–90s，30s 会把正常请求强杀成 504 并迫使前端落本地兜底（2026-10-11 实测）
- 5xx 重试一次（退避 `400ms × attempt`）；4xx 与超时**不重试**（`llmProxy.js:22-46`）
- **非流式** `stream:false`；无 SSE、无 WebSocket
- 请求体上限 2MB、`messages` 上限 200 条
- 出站前统一脱敏（邮箱/网址/电话/长数字），见 `public/modules/core/privacy.js`
- 搜索始终执行来源域名白名单（`server/config.js:37`），且绝不发送对话原文

## 4. 核心机制现状

### 4.1 关系状态（两块正交，都刻意不测心理）

- **阶段**：7 档离散标签（`public/modules/core/stages.js`）：刚加微信后的第一晚 / 隔天轻联系 / 第一次邀约 / 第一次约会后 / 暧昧推进 / 表达好感 / 确定关系。
- **投入度 L0–L4**：`public/modules/core/investment.js` 纯函数，从**可观测行为**计算（提问比、消息长度、主动性、自我暴露深度、引用前文、未来指向、关心语），输出 `evidence[]`、`confidence`、`sampleSize`；**置信度不足一律降一档**（宁可低估）。策略矩阵 `阶段分组 × 投入度 → observe / hold / advance / retreat`（`investment.js:68-72`），`retreat` 时对 A/B/C 施加硬约束。
- 服务端另有一套确定性 runtime（`server/relationshipIntelligence.js` + Skill 的 `runtime/state/state-machine.mjs`、`runtime/memory/memory-store.mjs`），需显式 consent 才保存结构化复盘记忆，且**不返回原始消息文本**。

> 设计判断：外部方案常建议 `familiarity/trust/affinity/conflict` 四维好感数值，本项目**有意拒绝**——不可验证的心理推断。同类开源实现里 FreeChat 也显式注入"没有亲密度数值、没有模板"。

### 4.2 记忆（**当前最大弱项**）

`public/modules/core/memory.js`：

- 提取方式是 **26 个硬编码关键词**（`extractTopics`）+ **3 条正则**（`detectCommunicationPatterns`、`inferInterest`）
- 形状：`background / interests / boundaries` 三个裸字符串 + `memoryTimeline[]` + `conversationSummaries[]` + `learnedPreferences`
- 注入只取"时间线最后 3 条 + 最近一次会话摘要"
- **完全没有**：向量、embedding、混合检索、评分排序、冲突消解、来源消息 ID、生效区间、取代标记
- 上限靠 `MEMORY_CONFIG`（摘要 20 条、时间线 100 条）硬裁，超限丢最旧

### 4.3 角色卡

自有 CCC 1.0 格式（`public/modules/core/character-card.js`），支持导入导出；**不兼容 SillyTavern V2/V3**，因此吃不到社区角色卡生态。内置 3 个角色，`systemRole` 是手写行为规则数组。

### 4.4 教练输出契约

`public/modules/coach/prompts.js` + `parser.js` + `evidence-contract.js`：模型输出 JSON，字段 `herReply / herIntent / yourGoal / judgement / risk / replyOptions(A/B/C) / recommendation / coachScore / evidenceReasoning`。主面板只渲染**可核对**的五张卡（行为观察 / 可能解释与反证 / 你的明确目标 / 目前未知 / 风险提醒）；`judgement` 不进主面板，仅在 `render/coach-float.js:34` 作为 `summary` 兜底——这是刻意的认知卫生设计，不是遗漏。解析器有多层降级：JSON → 宽松 JSON → 纯文本正则 → 本地模板。

### 4.5 完全没有的能力

群聊/多角色调度、主动消息、prompt 内时间感知、世界书/关键词触发注入、上下文压缩与摘要版本化、流式输出、断线恢复、消息幂等键。

### 5.3 过程中抓到并修掉的真实 bug

她的回复一落盘，`core/request-scope.js` 的上下文快照随之变化，**教练调用回来必被判为过期而丢弃**——整轮只剩她的回复，且外层 catch 会把提交阶段的真实错误也当过期静默吞掉。

修法：教练调用另开 `dialogue-coach` 通道、在落盘**之后**取快照；外层 catch 改用 `coachTicket || ticket` 判断。

补了回归测试 `test/request-scope.test.mjs`「她的回复落盘改变会话上下文后，教练分析结果仍必须提交」，并**反向验证**：把判断改回旧写法，该测试确实失败。原先测不出来是因为 VM 层测试用了常量上下文桩。

## 8. 给分析 AI 的操作注意事项

1. **中文路径 + GBK 控制台是这台机器的硬坑**：内联命令里的中文会变乱码字面量；需要跑含中文的脚本时必须写成 UTF-8 的 `.py`/`.mjs` 文件再执行。
